# C-23 is **not** the GPU. The camera segfaults on an RTX 4090 too.

2026-08-22. C-23's standing disposition is *"it is the GPU. Do not work around it"*
(Mohammed, 2026-08-19), taken after five crashes for five on an RTX 4080 SUPER 16 GB.
Every camera-dependent item in this campaign — the aligned-depth check, the C-21 clip,
`ferox_vision`/E-1, MM6, MM7, and the montage's PiP camera track — has been queued
behind "a 4090 day" on that basis.

**This box is that 4090, and the camera crashes on it identically.**

## The run

```
nvidia-smi: NVIDIA GeForce RTX 4090, 24564 MiB, driver 580.105.08
ROBOT=g1 TWIN=1 TWIN_CAMERA=1 TWIN_LIDAR=1 HAND=dex5_1p SIM_WORLD=hospital CAMERA_TF=1
```

```

       (HFOV 70.36 deg, VFOV 43.25 deg)
```

The camera is created successfully and its intrinsics read back correctly. The process

C-23 always died:

## The controlled comparison, on this same box, today

| configuration | result |
|---|---|
| `TWIN_CAMERA=0` (camera device skipped) | **boots and runs** — every C-39 and grasp run this session, dozens of boots |
| `TWIN_CAMERA=1` | **segfault**, first `world.step()` after the render product |

Same GPU, same driver, same image, same world, same asset. The only difference is the
camera device.

## What this does and does not establish

**Establishes:** the crash is *not* a property of the RTX 4080, and "get a 4090" does
not fix it. Memory was already ruled out by C-23's own measurement (peak 3776 MiB of
16376); this box has 24 GB and never gets near it. The failure is in Isaac 5.1's
synthetic-data / ROS 2 image-writer path.

**Does not establish:** the root cause. And one honest asymmetry must be recorded rather
than glossed: `RESUME.md` describes the working box as an **RTX 4090 with 48 GB**, and
this is a **24 GB** 4090. Both are "RTX 4090" by name and by the gate this brief sets.
Either the earlier box differed in something other than the model name, or the camera
path was never actually exercised there. I cannot settle which from here, and the
distinction matters to whoever picks this up.

## Consequence for the campaign

The camera-dependent backlog is **not** waiting on hardware procurement. It is waiting on
a software defect in the image-writer path, which means:

* MM0.2 aligned-depth check, the C-21 live re-proof, E-1/`ferox_vision`, MM6, MM7 and the
  montage's camera track stay blocked, but for a **different reason than recorded**;
* the next attempt should go at the writer itself — the offscreen render path works on
  this class of box (C-23's own control), so a capture route that avoids
  `ROS2CameraHelper`/`omni.graph.image` is the obvious thing to try, and it is a code
  change rather than a machine.

**C-23 should be reopened with its cause changed from "environment/GPU" to "Isaac 5.1
image-writer defect, reproduced on 4080 and 4090".**
